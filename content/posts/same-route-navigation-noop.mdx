모바일 앱 웹뷰에서 운영하는 서비스에서 제보가 왔다. 혜택 화면의 "쿠폰함
가기" 버튼이 **한 번은 되는데, 뒤로 갔다가 다시 누르면 안 된다**는 것.

재현해 보니 정확했다. 첫 클릭은 정상 이동, 두 번째 클릭은 무반응.
에러도 없다. 콘솔도 조용하다.

## 라우터는 시키는 일을 정확히 했다

원인은 라우터가 아니라 내 기대에 있었다. 이동 흐름이 이랬다.

1. 혜택 화면(`/benefit`)에서 버튼 클릭 → `/coupon?tab=unused`로 push
2. 쿠폰함에서 탭을 바꾸면 URL이 `/coupon?tab=used`로 replace
3. 뒤로가기 → 혜택 화면
4. 다시 버튼 클릭 → `/coupon?tab=unused`로 push... **인데 화면이 안 바뀐다**

3번에서 뒤로 갔을 때 히스토리 상태와 화면 상태가 어긋나 있었다. 게다가
쿠폰함 화면은 탭 상태를 URL이 아니라 **컴포넌트 state로도** 들고
있었는데, 같은 라우트로 재진입하면 컴포넌트가 리마운트되지 않으니
state 초기화 코드가 다시 돌지 않았다. 화면은 "이미 그 상태"라고 믿고,
사용자는 "아무 일도 안 일어났다"고 느낀다.

## 이동은 URL 변경이 아니라 상태 전이다

멀티 페이지 사이트에서 이동은 문서 전체의 재로딩이라 "가면 초기화된다"가
공짜로 보장된다. SPA에서는 그 보장이 없다. 같은 라우트로의 이동은
프레임워크에 따라 no-op이거나, 컴포넌트를 유지한 채 params만 바꾼다.

그래서 고치는 방법도 "이동을 고치는" 게 아니라 **상태의 원천을 하나로
줄이는** 것이었다.

- 탭 상태의 원천을 URL 쿼리 하나로 통일했다. state 복제본을 없애니
  "URL은 바뀌었는데 화면은 그대로"인 조합 자체가 사라진다.
- 재진입 시 초기화가 필요한 값은 마운트가 아니라 **쿼리 변화에 반응**
  하도록 옮겼다.

```tsx
// before: 마운트에 한 번 — 재진입하면 안 돈다
useEffect(() => { setTab(initialTab); }, []);

// after: 원천(쿼리)이 바뀔 때마다 — 재진입도 이동이다
const tab = router.query.tab ?? "unused";
```

## 남은 것

이 버그의 교훈은 하나다. **화면에 보이는 상태가 두 곳에 살면, 언젠가
두 곳이 서로 다른 말을 한다.** 그 뒤로 새 화면을 만들 때 "이 상태의
원천은 어디 하나인가"를 먼저 정하는 습관이 생겼다. URL이 원천이면
state 복제를 만들지 않고, state가 원천이면 URL에 그림자를 남기지 않는다.
