CS 처리 등으로 PG사 관리자 콘솔에서 결제를 직접 취소하는 일이
가끔 있다. 문제는 그 순간 서비스 DB는 아무것도 모른다는 것이다.
우리 서버를 거치지 않고 PG에서 바로 취소됐으니까. 이 사실을
전달받는 유일한 통로가 PG사의 웹훅이다.

웹훅 한 건이 도착한 뒤 무슨 일이 일어나야 하는지, 그리고 결제가
1:N으로 쪼개지는 도메인에서 그 처리가 어떻게 연쇄돼야 하는지를
정리한다.

## 웹훅은 이벤트가 아니라 동기화 신호다

웹훅 페이로드에 "취소됨"이 적혀 있어도 그걸 믿고 바로 취소 처리를
하지 않는다. 웹훅은 재전송되고, 중복되고, 순서가 뒤바뀔 수 있다.
그래서 처리 순서를 이렇게 뒀다.

1. 웹훅의 주문번호로 내부 결제를 **락을 걸고** 조회한다
   (`SELECT ... FOR UPDATE`) — 같은 결제에 웹훅이 동시에 두 번
   오는 경쟁 조건 방지.
2. 페이로드를 믿는 대신 **PG API를 다시 조회**해서 현재 상태를
   받아온다.
3. PG의 상태를 내부 결제 상태로 매핑한다.
   `CANCELED → PaymentStatus.CANCELED` 같은 닫힌 when 분기.
4. **상태가 실제로 바뀐 경우에만** 도메인 후처리 핸들러를 실행한다.
   같으면 그대로 return — 중복 웹훅은 여기서 무해해진다.

후처리는 `supports(payment)` / `handle(payment)` 인터페이스의
구현체들이 도메인별로 맡는다. 일반 예약, 장기 예약, 부가상품
주문이 각자의 핸들러를 갖고, 웹훅 서비스는 어느 도메인의
결제인지 모른 채 지원하는 핸들러만 골라 실행한다.

## 문제 — 결제가 1:N인 도메인

장기 예약은 투숙료가 월 단위로 쪼개져서 예약 하나에 결제가 여러
건이다. 1월분·2월분·3월분이 각각 PAID로 살아 있는데 그중 한 건이
PG 콘솔에서 취소됐다면, 예약 자체가 취소된 것이므로 **나머지
결제도 전부 취소돼야 한다.**

기존 핸들러는 이 연쇄를 절반만 하고 있었다.

- 연관 결제들의 취소 **히스토리만 저장**하고, PG에 실제 취소
  요청은 보내지 않았다. PAID인 결제가 그대로 남는다.
- 히스토리를 만들 때 취소 내역이 없으면 예외를 던졌다. 연관 결제
  중 하나라도 취소 내역이 비어 있으면 **전체 루프가 중단**됐다.

## 개선 — 상태별로 다르게, 실패해도 계속

핵심은 연관 결제를 상태별로 다르게 다루는 것이다.

```kotlin
for (related in relatedPayments) {
    if (related.id == payment.id) {
        savePaymentHistory(related)   // 지금 취소 중인 건 — 기록만
        continue
    }
    try {
        when (related.status) {
            PAID, PARTIAL_CANCELED ->
                paymentService.cancel(related.id, related.amount)
                // 실제 PG 취소 요청. 히스토리는 여기서 안 남긴다
            CANCELED ->
                savePaymentHistory(related)   // 이미 취소됨 — 기록만
            else -> Unit                      // PENDING·FAILED 등 — 스킵
        }
    } catch (e: Exception) {
        logger.error("연관 결제 취소 실패: id=${related.id}", e)
        // 한 건이 실패해도 나머지는 계속 진행
    }
}
```

`savePaymentHistory`는 취소 내역이 없으면 예외 대신 경고 로그만
남기고 스킵하도록 분리했다. 예외가 나야 할 곳(실제 취소 실패)과
그냥 넘어가도 되는 곳(기록할 내역 없음)을 구분한 것이다.

## 재귀 — cancel이 다시 핸들러를 부른다

`paymentService.cancel()`이 성공하면 그 결제의 상태가 바뀌고,
상태가 바뀌면 같은 핸들러가 **다시 실행된다.** B를 취소하면 B의
핸들러가 돌면서 연관 결제 A·B·C를 다시 조회하는 재귀 구조다.

무한 루프처럼 보이지만 종료가 보장된다. 재실행 시점에 A는 이미
CANCELED라 히스토리만 남기고, PAID였던 C만 실제 취소로 넘어간다.
전부 CANCELED가 되는 순간 **상태 변경이 없으므로 핸들러 자체가
실행되지 않는다.** 루프를 코드(방문 목록 같은 것)로 막은 게
아니라, "상태가 바뀔 때만 실행된다"는 앞 단의 규칙이 종료 조건을
공짜로 준 셈이다. PAID 분기에서 히스토리를 안 남기는 이유도
같다 — 재실행된 핸들러가 어차피 남기니까, 남기면 중복이 된다.

## 정직하게 남은 것

각 `cancel()`은 독립 트랜잭션이다. C 취소가 실패해도 이미 취소된
B는 롤백되지 않는다. 지금은 에러 로그로 추적해 수동 처리하는
정도고, 보상 트랜잭션은 숙제로 남아 있다. 연관 결제가 수십 건이
되면 동기 재귀도 부담이라 비동기 전환을 검토해야 한다.

## 설계 검토에 쓴 프롬프트

이 핸들러를 짤 때는 비슷한 구현체가 이미 둘 있었고, 새 도메인은
취소 경로가 그들과 미묘하게 달랐다. 코드를 다 짜기 전에 AI에게
설계 검토를 시켰는데, 실제로 쓴 프롬프트를 줄이면 이렇다.

```text
@.../PaymentStatusChangeHandler 구현체의 handleCanceled를 짜면서
고민이 있어. 다른 구현체와 달리 이 도메인은 PG 콘솔에서 직접
취소되는 경우가 거의 없어 — 주문 취소와 결제 취소가 별개 플로우로
돌고, 취소 검증에 실패해도 재고 복구는 이미 진행되거든. 그래서
앱 API(@.../Controller의 cancel)의 로직과 비슷하게 구현하려고 해.
어드민용 취소 API는 검증 가짓수가 더 적고, 부분취소 API도 따로
있어서 이것까지 고려해야 할지 고민이야.

1. 내가 고려 못한 부분이 있는지
2. 어드민 부분취소에 대응 가능한 구조인지
3. 주석 처리해둔 알림 발송·주문 상태 변경 함수를 어떻게 처리할지
검토해줘.
```

파일을 첨부하는 것보다 중요했던 건 가운데 문단이다. "이 도메인은
PG 콘솔 취소가 드물다", "검증이 실패해도 재고는 이미 복구된다"
같은 **운영 사실은 코드 어디에도 적혀 있지 않다.** AI는 코드는
읽어도 그건 모른다. 도메인 배경을 서술해서 넘기자 "부분취소 대응은
지금 구조에서 가능하되 금액 검증 위치가 문제"라는, 코드만 보면 안
나오는 수준의 답이 돌아왔다.

취소 하나가 취소 셋을 부르는 구조는 결국 상태 머신의 규칙 —
"바뀔 때만 반응한다" — 하나로 지탱된다. 그 규칙이 앞 단(웹훅
동기화)에 있었기 때문에 뒷 단(연쇄 취소)이 단순해질 수 있었다.
