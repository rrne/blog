프로젝트마다 컨벤션과 환경 설정이 달랐다. 어떤 레포는 큰따옴표,
어떤 레포는 작은따옴표. 누가 어떤 프로젝트를 수정하든 빠르게 코드를
파악하고 적은 리소스로 기여할 수 있으려면 스타일이 통일돼야 했다.
그래서 팀 컨벤션 문서를 만들었다.

바닥부터 발명하지는 않았다. [Airbnb JavaScript Style
Guide](https://github.com/airbnb/javascript)를 기반으로 하고
[Google JavaScript Style
Guide](https://google.github.io/styleguide/jsguide.html)를 참고하되,
내부 상황에 맞게 조정했다. 이 글은 그 문서의 요약이다 — 규칙과
함께, 각 규칙을 고른 이유를 남긴다.

## 변수 — const 우선, 한 줄에 하나

`var`는 쓰지 않는다. 재할당이 없으면 `const`, 있으면 `let`.
선언은 한 줄에 하나씩 한다 — comma로 다중 선언하면 변수를
추가·삭제할 때 diff가 지저분해지고, 디버거에서 할당이 한 번에
잡혀 단계별 확인이 안 된다.

```js
// bad
const salesList = getTimeSaleList(),
    isTimeSale = true;

// good
const salesList = getTimeSaleList();
const isTimeSale = true;
```

`const`를 먼저 모아 선언하고 `let`을 뒤에 둔다. 그리고 변수는
파일 상단이 아니라 **쓰이는 곳 가까이에서** 할당한다 — 이른
return으로 함수가 끝나면, 그 아래에서만 쓰일 값을 미리 계산한 게
낭비가 되기 때문이다.

## 문자열 — 작은따옴표, 연결 대신 템플릿 리터럴

문자열은 작은따옴표로 감싼다. 긴 문자열도 `+`로 줄을 쪼개지
않는다 — 쪼개진 문자열은 검색이 안 걸린다. 값을 끼워 넣을 때는
`+` 연결 대신 템플릿 리터럴을 쓴다.

```js
// bad
const introduce = 'Hello my name is ' + name + '..!';

// good
const introduce = `Hello my name is ${name}..!`;
```

## 객체·배열 — 리터럴로 만들고, 메서드로 다룬다

`new Object()`, `new Array()` 대신 `{}`, `[]`. 객체 속성이 변수와
이름이 같으면 shorthand로 적고, shorthand 속성들을 **앞쪽에
모은다** — 어떤 속성이 축약인지 한눈에 구분된다.

```js
// good
const userObject = {
    age,
    nickname,
    job: 'developer',
};
```

배열에 값을 넣을 때는 인덱스 대입이 아니라 `push`, 복사할 때는
for 루프가 아니라 spread(`[...arr]`)를 쓴다.

## 비교 — 타입마다 규칙이 다르다

`===`와 `!==`만 쓴다. 조건문 축약은 타입별로 다르게 간다 —
불리언은 축약하고, 문자열과 숫자는 명시적으로 비교한다.

```js
// 불리언 — 축약
if (isNewBrand) { ... }

// 문자열·숫자 — 명시적 비교
if (name !== '') { ... }
if (categories.length > 0) { ... }
```

`if (name)`은 빈 문자열과 undefined를 구분하지 못한다. 축약이
줄여주는 글자 수보다, "이 조건이 정확히 뭘 거르는가"가 드러나는
쪽이 더 값지다.

삼항 연산자는 중첩하지 않고, 중첩이 필요하면 변수로 나눈다.
연산자를 혼용할 때는 괄호로 우선순위를 표시한다 —
`(a && b < 0) || (c > 0)`처럼, 읽는 사람이 우선순위 표를 떠올리지
않아도 되게.

## 블록 — else보다 이른 return

여러 줄 블록에는 항상 중괄호를 쓴다. if가 return으로 끝나면
else를 만들지 않는다.

```js
// bad
if (isCat) {
    return 'meow';
} else {
    return 'nope';
}

// good
if (isCat) {
    return 'meow';
}

return 'nope';
```

들여쓰기 깊이가 곧 읽기 난이도다. 이른 return은 "이 아래는 그
경우가 아니다"를 보장해서, 남은 코드를 읽을 때 머리에 들고 있어야
할 조건을 줄여준다.

## 함수 — 표현식으로, 파라미터는 건드리지 않는다

함수는 선언문 대신 **이름 있는 함수 표현식**으로 쓴다. 선언문은
호이스팅돼서 정의보다 앞에서 호출할 수 있는데, 그게 가능하다는
사실 자체가 코드 읽는 순서를 흐트러뜨린다.

파라미터는 함수 안에서 재할당하지 않는다. 기본값이 필요하면
default parameter로 선언하고, 기본값 있는 파라미터는 마지막에
둔다. `arguments` 객체 대신 rest(`...args`)를 쓴다.

```js
// bad
function getPosts(opts) {
    opts = opts || {};
}

// good
function getPosts(opts = {}) { ... }
```

객체를 받는 함수는 파라미터에서 바로 구조 분해한다.

```js
// best
function getUserName({ firstName, lastName }) {
    return `${firstName} ${lastName}`;
}
```

화살표 함수는 익명 함수 자리(콜백)에 쓰고, 로직이 복잡해지면
이름 있는 함수로 뺀다. 단일 표현식이면 중괄호와 return을 생략한다
— `arr.map(item => item + 1)`.

## 모듈 — import/export, 와일드카드 금지

`require` 대신 `import`/`export`. `import *` 와일드카드는 쓰지
않는다 — 무엇을 가져왔는지가 코드에 드러나지 않기 때문이다. 같은
경로의 모듈은 한 줄로 합친다. import한 것을 같은 줄에서 바로
export하는 것도 지양한다 — 한 줄이 줄지만 import/export의 일관성이
깨진다.

```js
// good
import validate, { nameValidate, emailValidate } from 'calculator';
```

## 규칙보다 중요한 것

문서를 만들며 확실해진 게 하나 있다. 컨벤션의 가치는 개별 규칙의
옳고 그름이 아니라 **같은 논쟁을 두 번 하지 않는 데** 있다.
작은따옴표든 큰따옴표든 반나절 토론할 주제가 아니다 — 한 번 정하고,
문서에 적고, 다음부터는 코드 리뷰에서 스타일 얘기가 사라지는 것.
그게 목적이다.

그래서 다음 단계는 이 문서를 사람이 아니라 도구가 지키게 하는
것이다. 여기 적은 규칙 대부분은 ESLint + Prettier 설정으로 강제할
수 있고, 그렇게 되면 문서는 "왜 이렇게 정했는가"의 기록으로
남는다. 규칙은 도구가, 이유는 문서가 맡는 분업이다.
