탭 컴포넌트가 서비스 곳곳에서 쓰이는데, 화면마다 생김새가 달랐다.
밑줄이 움직이는 탭, 알약 버튼 탭, 가로 스크롤 목록 탭. 처음에는
prop을 하나씩 추가하며 버텼다 — `hasBorder`, `scrollable`,
`buttonLike`… boolean prop이 셋을 넘는 순간 조합의 수는 여덟이 되고,
그중 실제로 의미 있는 조합은 셋뿐이었다.

## 모양에 이름을 붙인다

문제는 스타일이 아니라 어휘였다. 디자이너와 나는 "버튼형 탭"이라고
부르는데 코드에는 그 이름이 없었다. 그래서 variant를 타입으로
선언하는 것부터 시작했다.

```ts
type TabType = 'BUTTON' | 'LINE' | 'LIST';
```

boolean 조합이 아니라 **닫힌 목록**이다. 존재하지 않는 조합은 타입
수준에서 존재하지 않는다.

## 분기 대신 데이터

다음은 스타일. variant마다 if나 삼항으로 갈라치던 것을, variant를
키로 갖는 룩업 맵 하나로 바꿨다.

```ts
const TabTypeStyle = {
  LINE: {
    tabsLabel: { gap: 10, padding: '0 32px', height: '58px' },
    tabsButton: { border: 'none', '&.active': { fontWeight: 600 } },
  },
  LIST: {
    tabsLabel: { justifyContent: 'start', overflowX: 'auto' },
    tabsButton: {
      whiteSpace: 'nowrap', color: '#ccc',
      '&.active': { color: 'black', fontWeight: 700 },
    },
  },
  BUTTON: {
    tabsLabel: { background: '#f8f8f8', border: '1px solid #ddd' },
    tabsButton: {
      borderRight: '1px solid #ddd',
      '&.active': { background: 'white', border: '1px solid black' },
    },
  },
};
```

컴포넌트 본문은 조회만 한다.

```tsx
const Tab = ({ type = 'LINE', ...props }: TabProps) => {
  const styles = TabTypeStyle[type];
  return <TabsLabel css={styles.tabsLabel}>...</TabsLabel>;
};
```

이 전환의 핵심은 스타일이 **코드(분기)에서 데이터(맵)로** 옮겨간
것이다. 데이터가 되면 좋은 일이 연쇄적으로 생긴다.

- 새 variant 추가 = 맵에 항목 하나. 본문은 안 건드린다.
- 타입과 맵의 키가 어긋나면 컴파일 에러 — `TabType`에 추가하고 맵에
  안 넣으면 조회가 `undefined`가 될 수 있음을 타입이 알려준다.
- variant 간 차이가 한눈에 비교된다. if 분기에서는 흩어져 보이지
  않던 것.

## 이게 디자인 시스템의 씨앗이다

[CVA](https://cva.style) 같은 variant 라이브러리가 하는 일이 정확히
이것이다 — variant 이름의 닫힌 목록, 이름→스타일 룩업, 기본값. 손으로
한 번 만들어보면 라이브러리를 도입할 때 "마법"이 아니라 "우리가 하던
것의 정리"로 보인다.

그리고 한계도 정직하게 보인다. 이 탭은 라벨이 다섯 개를 넘으면
줄바꿈이 생기는 문제를 TODO로 안고 있었다 — variant 시스템은 모양의
분기를 정리해주지만, **레이아웃의 한계값 같은 건 여전히 설계자가
알아야 한다.** 맵은 어휘를 정리하는 도구지 디자인을 대신 해주는
도구가 아니다.

작게 시작하자. 컴포넌트 하나, variant 타입 하나, 룩업 맵 하나.
디자인 시스템은 패키지를 만드는 데서가 아니라 이름을 합의하는 데서
시작된다.
