화면 하단이 잘린다는 제보였다. 바텀 버튼이 어떤 기기에서는 보이고,
어떤 기기에서는 반쯤 가려졌다. 단순한 CSS 높이 문제라고 생각했고,
첫 PR은 10분 만에 올라갔다.

그 티켓에는 결국 **PR이 다섯 개** 붙었다. 고칠 때마다 다른 기기,
다른 상황에서 깨졌기 때문이다. iOS에서 고치면 Android 키보드가 올라올
때 깨졌고, 그걸 고치면 웹뷰가 아닌 브라우저에서 깨졌다.

## 100vh는 하나의 값이 아니다

데스크톱에서 `100vh`는 명확하다. 모바일에서는 아니다 — 브라우저
주소창이 스크롤에 따라 나타났다 사라지고, 그때마다 "보이는 영역"의
높이가 변한다. 그런데 `100vh`는 **주소창이 사라진 상태의 최대 높이로
고정**돼 있다. 주소창이 떠 있는 동안 `100vh`짜리 요소의 아래쪽은 화면
밖에 있다. 바텀 버튼이 잘린 이유다.

앱 웹뷰라고 자유롭지 않다. 웹뷰는 주소창이 없는 대신 네이티브 내비게이션
바, 홈 인디케이터(safe area), 그리고 **키보드**가 같은 자리를 두고
경쟁한다. 특히 키보드가 올라올 때 viewport가 줄어드는지, 화면이 밀리는지는
OS와 웹뷰 설정에 따라 다르다. "기기마다 다르게 깨진" 이유다.

## 다섯 개의 PR이 가르쳐준 것

지금이라면 처음부터 이렇게 간다.

**① 고정 높이가 정말 필요한지부터 의심한다.** 대부분의 화면은
`min-height`와 일반 문서 흐름으로 충분하다. `100vh` 풀스크린 레이아웃은
필요한 화면에만.

**② 새 viewport 단위를 기본으로.** 이 문제가 하도 흔해서 CSS에 단위가
새로 생겼다.

```css
/* 주소창 상태에 따라 '동적으로' 변하는 높이 */
height: 100dvh;
/* 가장 작을 때 기준(주소창 떠 있음) — 절대 잘리면 안 되는 것에 */
height: 100svh;
```

바텀 버튼처럼 "항상 보여야 하는" 요소는 `svh` 기준으로 배치하면
어떤 상태에서도 잘리지 않는다.

**③ safe area는 덧셈으로.**

```css
padding-bottom: calc(16px + env(safe-area-inset-bottom));
```

**④ 키보드는 CSS만으로 안 끝난다.** 키보드 위에 버튼을 띄워야 하는
화면은 `visualViewport` API로 실제 보이는 높이를 구독하는 게 유일하게
전 기기에서 일관적이었다.

```ts
visualViewport?.addEventListener("resize", () => {
  setViewportHeight(visualViewport.height);
});
```

## 진짜 교훈은 프로세스에 있다

기술적 원인보다 오래 남은 교훈은 이것이다. **한 티켓에 수정이 세 번
이상 붙으면, 그건 수정이 아니라 이해가 부족하다는 신호다.** 세 번째
PR을 올리기 전에 멈추고 "이 문제의 전체 지형이 뭔가"를 그렸어야 했다 —
기기 × 키보드 × 웹뷰/브라우저 매트릭스를 먼저 그리고 나서야 다섯 번째
PR이 마지막 PR이 됐다.
