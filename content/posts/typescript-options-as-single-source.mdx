정산 어드민을 만들다 보면 셀렉트 박스가 끝없이 나온다. 결제수단,
영수증 상태, 지급 상태, 비용 귀속… 그리고 매번 같은 코드 두 벌을
쓰게 된다.

```ts
// 1. 화면에 뿌릴 옵션 배열
const PaymentMethod = [
  { value: 'CASH', label: '현금(계좌이체)' },
  { value: 'CORP_CARD', label: '법인카드' },
  { value: 'PERSONAL_CARD', label: '개인카드(경비청구)' },
];

// 2. 검색 조건의 타입
type ExpenseSearch = {
  paymentMethod: 'CASH' | 'CORP_CARD' | 'PERSONAL_CARD' | null;
};
```

같은 지식이 두 곳에 있다. 결제수단이 하나 추가되면 두 곳을 고쳐야
하고, **한 곳만 고친 날이 반드시 온다.** 옵션에는 있는데 타입에는
없는 값 — 컴파일러는 통과시키고 런타임에서 어긋난다.

## 배열에서 타입을 뽑아낸다

타입스크립트는 값에서 타입을 파생시킬 수 있다. 옵션 배열을 단일
소스로 두고, 타입은 거기서 꺼내 쓰면 된다.

```ts
type ExpenseSearch = {
  paymentMethod: (typeof PaymentMethod)[number]['value'] | null;
};
```

읽는 법은 바깥부터가 아니라 안쪽부터다.

- `typeof PaymentMethod` — 값의 타입. 옵션 객체의 배열.
- `[number]` — 배열을 숫자로 인덱싱하면 원소 타입이 나온다.
- `['value']` — 원소에서 value 프로퍼티의 타입만 꺼낸다.

이제 옵션을 추가하면 타입이 저절로 넓어진다. 정산 화면 하나에서 이
패턴을 스무 곳 넘게 썼다 — 상태값 종류가 아홉 개쯤 되면 이중 관리는
선택지가 아니다.

## 함정: as const가 없으면 전부 string이다

그런데 처음 쓴 버전에는 구멍이 있었다. 위 코드 그대로면
`(typeof PaymentMethod)[number]['value']`는 `'CASH' | 'CORP_CARD' |
'PERSONAL_CARD'`가 아니라 **그냥 `string`이다.**

타입스크립트는 `const` 선언이어도 객체 프로퍼티를 넓혀서 추론한다.
`value: 'CASH'`는 `value: string`이 된다 — 나중에 재할당될 수 있는
자리라서다. 그래서 유니온 타입을 기대하고 썼지만 실제로는 아무
문자열이나 통과하고 있었다. 타입은 거짓말을 하지 않지만, **타입이
뭐라고 추론됐는지 확인하지 않으면 내가 나에게 속는다.**

고치는 건 두 글자다.

```ts
const PaymentMethod = [
  { value: 'CASH', label: '현금(계좌이체)' },
  { value: 'CORP_CARD', label: '법인카드' },
  { value: 'PERSONAL_CARD', label: '개인카드(경비청구)' },
] as const;

type Method = (typeof PaymentMethod)[number]['value'];
// 'CASH' | 'CORP_CARD' | 'PERSONAL_CARD'
```

`as const`는 "이 값은 이대로 고정"이라는 선언이고, 그제서야 리터럴
타입이 보존된다. 오타 난 상태값이 컴파일 에러가 되는지 — 파생 타입을
만들었으면 일부러 틀린 값을 넣어서 한 번은 확인해봐야 한다.

## 어디까지 밀어붙일까

이 패턴의 손익분기는 명확하다. **UI에 뿌릴 목록과 코드에서 분기할
값이 같은 집합일 때** 강력하다. 반대로 서버가 내려주는 값이 소스인
경우라면 배열이 아니라 API 스키마에서 타입을 가져와야 한다 — 단일
소스 원칙은 같고, 소스의 위치만 다르다.

두 벌의 코드가 같은 지식을 표현하고 있다면, 하나를 지우고 남은
하나에서 파생시킬 방법부터 찾자. 타입스크립트는 그 방향의 도구를
생각보다 많이 갖고 있다.
